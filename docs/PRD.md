# Signal-to-Ship｜MVP 产品定义

## 1. 定位

**Signal-to-Ship** 是面向初中级开发者和求职者的证据驱动项目发现器。它不回答“有什么热门项目可做”，而是帮助用户从公开讨论中筛出可被复核的真实痛点，并将一个痛点簇转成适合其技术栈的 MVP 蓝图。

首个用户是：正在投递全栈/AI 工程岗位、拥有 2–3 周业余开发时间、已有 TypeScript 或 Python 基础、却难以决定下一件作品该做什么的个人开发者。

## 2. 要解决的任务

用户输入：

- 一个问题主题，例如「个人开发者的信息过载」；
- 目标岗位和想证明的技能；
- 5–30 个公开 URL，或允许系统从 GitHub Issues / Hacker News 检索。

用户得到：

1. 可点开的原始证据和摘录；
2. 按语义合并后的痛点簇，而不是一串链接；
3. 有明细的机会评分；
4. 1–3 个候选项目卡；
5. 一个可在 7 天完成的 MVP 范围、架构和验收标准。

## 3. 核心用户流（首版）

1. 用户建立 Workspace，填写目标职位、技术栈与开发时间。
2. 用户粘贴 URL，或提交一个搜索主题。
3. 系统异步抓取正文，保留 URL、标题、抓取时间和可引用段落。
4. 系统从每个来源抽取结构化 Signal：`问题、谁受影响、现有替代方案、原文证据、具体性、风险`。
5. 系统以嵌入相似度 + 关键词重叠聚类；用户可以查看每个簇中有哪些原始证据。
6. 系统计算分数，生成不超过 3 张项目卡；用户选中一张后，生成带范围约束的 7 天计划。

## 4. 非目标（MVP 不做）

- 不做“自动创办公司”、收入预测或泛化投资建议。
- 不抓取登录后内容，不绕过 robots、验证码或站点访问限制。
- 不把 LLM 结论伪装成事实：结论必须关联证据，低证据簇必须标记为“待验证”。
- 不在首版做团队协作、浏览器插件、定时推送和多语言。

## 5. 成功标准

| 指标 | MVP 验收线 |
| --- | --- |
| 来源可追溯 | 每张项目卡有 >= 3 条可访问来源及对应摘录 |
| 聚类质量 | 在 30 条演示样本上，人工抽查 10 对相似内容时 >= 8 对归类合理 |
| 透明评分 | 用户能看到每个分项、权重、扣分原因和版本号 |
| 可执行性 | 生成的计划包含 7 天以内任务、技术决策、明确不做项、验收标准 |
| 时间 | 30 个已允许来源在本地演示中 5 分钟内完成一次分析 |

## 6. 演示脚本

主题：**“开发者如何减少项目发现和研究时的信息债”**。

导入 20–30 个许可公开页面（GitHub Issues、Devpost、Hacker News）。展示：

1. 原始链接杂乱且难以比较；
2. 系统归并出“收藏后不复看”“项目选择成本高”“研究结果没有行动出口”等痛点簇；
3. 选择最高分簇，打开每个分项与原文；
4. 一键生成本项目的 7 天 MVP 计划；
5. 导出 Markdown，作为 GitHub Issue 或 README 初稿。
